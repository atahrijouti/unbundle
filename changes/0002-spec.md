# 0002 — Spec

Status: proposed

## Why

- Nothing describes what unbundle does; its behavior lives only in the code.
- Changing the code, or testing it, needs a record of today's behavior to check against.

## Shape

```
CONTEXT.md      the terms
spec/
  README.md     how a spec file is written
  <topic>.md    page, layout, metadata, scripts, import-map, static,
                config, staging, build, dev-server, errors, package
```

- Each rule states what the code does today, with an ID (`topic/concept/aspect`) that tests and change records can point at.
- Where the code isn't what's wanted, a TODO in that file says so.
- From here on, unbundle changes through a change record, then the spec, tests and code together.

## Breaking changes

None: no code changes.
